## Marketing — Comedian Promo Stunts — DECIDED
- Original plan: pay professional comedians to promote the app, including secretly roasting unsuspecting regular users as a promo stunt (they don't know in advance, get surprised by a "master" roaster).
- **DECIDED to keep this tactic, WITH two guardrails**:
  1. **Specific post-match consent from the surprised user** before any footage from that particular stunt is posted publicly — separate from standard recording consent, since being used as a marketing prop is a different situation from an ordinary match. If they decline, the clip stays private/unpublished.
  2. **Public disclosure/labeling when posted** — e.g. "Special Guest Battle" or naming the comedian — rather than presenting it as an ordinary random match. Rationale: presenting a staged encounter as fully organic risks deceptive-advertising concerns (same principle behind FTC sponsored-content disclosure rules) — the AUDIENCE watching the posted clip deserves to know it wasn't a random encounter, separate from the participant's own consent.

## Product Overview
A mobile app (Flutter, Android-first, iOS later) where users are randomly matched 1-on-1 for live 1v1 video roast battles. Winner is determined by community vote (skill-based, not chance). Competitive ranking system with tiers, tournaments, and prizes. Long-term goal: viral growth to 1M+ users, monetized via paid tournament entry fees.

Developer: solo, no prior backend experience, comfortable with cross-platform frameworks, working on Windows, low/no budget for V1. Based in San Diego, CA.

## Core Match Flow
- **Account creation**: phone number + email + password (encrypted). Age-gated via Google Play Age Signals API (see Age Verification below) — no manual ID verification for V1.
- **Onboarding tutorial — DECIDED**: mandatory before a user's first match (covers camera positioning/framing AND ground rules — mic muting, round timing, recording consent). One-time gate only — never replayed for returning users after first completion. **Format — DECIDED**: interactive practice round (not a passive video or slides) — user actually walks through a mock match flow to learn by doing.
- **Pre-match check**: camera preview with face-position guide ("hologram" framing overlay), prompts for good lighting/steady camera/loud enough audio. Both users must pass this before match starts.
  - **Build Order step 3 implementation status**: `PreMatchScreen` built with real camera preview + oval framing guide overlay + a REAL mic-level check (gates the "I'm Ready" button — via Agora's `enableAudioVolumeIndication`, only reports once joined to a channel). Lighting/steadiness/face-visible are advisory-only static prompts, NOT auto-detected. **CORRECTION (found during step 9a video-moderation research)**: this section previously claimed `registerVideoFrameObserver` was an unimplemented stub - that was WRONG, based on reading only the auto-generated binding file (`lib/src/binding/agora_media_engine_impl.dart`, which does contain a literal `throw UnimplementedError`) without checking that `RtcEngine.getMediaEngine()` actually returns a DIFFERENT, hand-written override class (`lib/src/impl/agora_media_engine_impl_override.dart`) with a real, working implementation wired to native code. Confirmed live on-device: registering a `VideoFrameObserver` and calling it before `joinChannel` (per Agora's docs) delivered continuous real `onCaptureVideoFrame` callbacks (3000+ frames, consistent 576×1024 I420 buffers) - this is NOT a blocker. See the Content Policy & Moderation section's step 9a status note for what this unblocks.
  - Recording Consent (see Legal Items below) is a separate screen shown BEFORE the pre-match camera check, per the "distinct affirmative action" legal requirement.
- **Auto quality flags**: AI/heuristic detection for too-dark, too-quiet, too-shaky, face not visible, mic muted, connection issues. Flagged matches are auto-cancelled and re-queued — NO score penalty either way, just a re-match prompt. This is a technical quality gate only, not content moderation. **Not yet implemented** — the pre-match mic check above is a one-time gate before a match starts, not the same thing as continuous in-match quality monitoring; the dark/shaky/face-visible detection gap noted above applies here too.
- **Quality-flag abuse safeguard — NEW, DECIDED**: since a disqualified match has no rating penalty and simply triggers a rematch, this creates a potential dodge mechanism (deliberately faking bad lighting/audio to escape a match that's going badly). DECIDED: add monitoring/safeguard against this — e.g., track/flag accounts with abnormally high disqualification-triggering rates for review, rather than treating every disqualification as automatically legitimate. Exact detection mechanism/threshold not yet designed — same theme as other abuse-prevention backlog items (vote fraud, multi-account collusion).
- **Match structure — DECIDED**: Random 1v1 pairing, same language only (English only for V1). **Standard format: 3 rounds, 15 seconds max per turn, used for BOTH exhibition and ranked modes** (tournament format may differ — TBD, could be longer for higher stakes).
- **Live match configuration — BUILT.** Round count, turn length, countdown and bio-reveal length are read from the `config/matchSettings` Firestore document (`functions/matchSettings.js`), not hardcoded — the developer can retune the format live, without shipping a new app version, which was the explicit requirement.
  - **Chose a Firestore document over Firebase Remote Config**, which this doc's schema explicitly permitted ("Remote Config or Firestore doc"). Three reasons, in order of importance: (1) settings are resolved **server-side once, at pairing time, and stamped onto the match document**, so both players provably run identical timings — with client-side Remote Config two devices can hold different cached values and the two halves of a match would silently disagree about how long a turn lasts, a bug that surfaces as "the timer felt wrong" rather than as an error; (2) no new Flutter dependency, so no risk to the AGP/KGP pin this doc documents as fragile; (3) editing it is the same "admin uses the Firebase console" workflow already used for profile approval, report review and tournament creation.
  - **Bounds are enforced server-side because this config is hand-edited in a console against a live app, with no validation layer in between.** A `roundCount` of 0 would end matches before they began; a `roundLengthSeconds` of 9999 would strand two people in a single turn for nearly three hours. Out-of-range or non-numeric values fall back **per field** — first to the top-level value, then to the documented default — so one bad override never discards the rest of a good configuration.
  - **Verified end-to-end against the deployed backend**: non-default values reach a real pairing and are stamped on the match document; both players receive byte-identical settings; a per-mode override applies to that mode only and leaves others untouched; `roundCount: 0` and `roundLengthSeconds: 9999` are both refused in favour of defaults. Plus 13 local checks on the merge/bounds rules. **Confirmed on a real device**: with `bioRevealSeconds` set to 20, the bio reveal counted down from 20 rather than the 60-second default.
  - `firestore.rules` allows any signed-in client to read `config/**` but **nobody** to write it — a client that could edit this would set its own turn length.
- **In-turn countdown timer — NEW, DECIDED**: a visible countdown timer during each player's turn (counting down the 15-second max). UI requirement: small, unobtrusive — should not take up significant screen space or distract from the video feed itself.
  - **MUST be a remote/backend-configurable value (e.g., Firebase Remote Config), NOT hardcoded** — developer wants to tune round count/length post-launch without shipping a new app version, to test what format performs best.
  - Each round: one player gets up to the max time to roast (can end turn early, no penalty for time used or joke count). Opponent's mic is muted during that turn.
  - Between turns: "Player X, get ready" screen + 5-second countdown, then roles swap.
  - After all rounds: both mics unmute (volume slightly lowered) while verdict is delivered.
  - Round format should be mode-based (exhibition/ranked/tournament each get one standardized format), NOT user-customizable per match — customization would fragment ranking data and complicate matchmaking.

    - **Live configuration is now BUILT** — round count, turn length, countdown and bio-reveal length all come from `config/matchSettings` rather than hardcoded constants, satisfying the "must be remotely configurable, NOT hardcoded" requirement above. See the dedicated note under the Firestore Data Model's `config/matchSettings` entry.
    - **Real matchmaking IS now built** (see the dedicated Matchmaking Queue Architecture status note below) — the hardcoded "test-channel" both devices used to join is gone, and each match gets its own server-assigned channel derived from a real `matches/{matchId}` document. `MatchScreen` now takes a `MatchPairing` (matchId, channelName, opponentId, mode) rather than assuming a shared test room.

Verified live: both devices showed correctly complementary turn banners ("Your turn coming up" vs. "Opponent's turn coming up") with synced countdown numbers, and both reached the verdict screen simultaneously.

The visible match behavior (banners, countdowns, both devices reaching verdict together) looked correct, so this weakly suggests a harmless dedup/logging artifact rather than a skipped turn, but this was NOT conclusively root-caused. Worth re-verifying with explicit turnIndex/phase logging before relying on this state machine for real matches.

- **Pre-match bio reveal — BUILT.** `BioRevealScreen` (`lib/screens/match/bio_reveal_screen.dart`) sits between matchmaking and `MatchScreen`, showing the opponent's profile fields plus their volunteered `ammoText` in its own highlighted card. Rank/rating is deliberately absent, per the decision below. Ends after 60s **or** as soon as both players tap Ready, whichever comes first — readiness goes through a `setMatchReady` Cloud Function (clients can't write the matches collection at all, and readiness has to be attributable so a client can't mark its *opponent* ready), and both devices learn about it by listening to the match document. A player whose profile is empty renders an explicit "left their profile blank, you're on your own" rather than a broken-looking empty screen. **Skip/decline is built alongside it**: `skipMatch` spends one of a documented **3 skips per day**, settles the match as `abandoned` + `voteFinalized` so it's never rated or voted on, and records `skippedByUserId` so the *other* player's listener can tell them their opponent passed. The counter (`skipsUsedToday`/`skipsResetDate`) is protected in `firestore.rules` exactly like `rating` — a client that could reset its own counter would have unlimited skips, which is precisely the opponent-cherry-picking the limit exists to prevent. Reset is keyed to the **UTC** day, not the player's local midnight, since no per-user timezone is stored — practical effect is the allowance resets at 5pm Pacific; fine for V1, worth revisiting if players notice. Verified end-to-end against the deployed backend (readiness accumulates and is idempotent; skipping settles the match, spends exactly one skip, blocks a second skip and any vote; the allowance runs out, refuses further skips, and is per-account), plus 6 more local checks covering the day-rollover reset. **Reveal length is live-configurable** via `config/matchSettings`'s `bioRevealSeconds` (see the Live match configuration note above), resolved server-side at pairing time so both players count down together.
- **Original decision, for reference**: after matchmaking pairs two users, show each user the opponent's profile bio (see User Profile System below) for up to 1 minute OR until both players tap "ready," whichever comes first. This gives roasters concrete material ("ammo") instead of relying purely on improv about a stranger's appearance. Full bio is shown pre-match only — NOT persistently visible during the actual roast (keeps video UI clean; also tests what the roaster actually remembers/uses). Optional future iteration: a small persistent one-line tag (name + profession only) pinned in a corner during the match — not required for V1, worth playtesting first. **DECIDED**: rank/rating is NOT shown during bio reveal — only the profile ammo fields (profession, interests, etc). Keeps focus on comedy material rather than skill intimidation/sandbagging psychology.
- **Skip/decline — BUILT** (see the Pre-match bio reveal entry above for the implementation, since the two ship together). Original decision: users may skip a proposed match after seeing the opponent's bio, before it starts. Limited to 2-3 skips per day (prevents cherry-picking "easy" opponents while still giving an escape hatch for a bad pairing); 3/day was chosen from that range.
  - **Known gap**: when one player skips, the other is shown "Your opponent passed on this one" and returned to Home — they are NOT automatically put back into the matchmaking queue, which is the better experience and the obvious next iteration.
- **Match-found notification — BUILT (push half).** `PushNotificationService` (`lib/core/services/push_notification_service.dart`) requests notification permission, stores this device's FCM token in `users/{uid}.fcmTokens` (an **array**, since one account can be signed in on a phone and a tablet per the Device support decision), keeps it current via `onTokenRefresh`, and removes it on sign-out so the next person on that device doesn't get the previous account's alerts. Registration happens in `_AccountStatusGate`, which is now keyed by uid so switching accounts builds fresh state instead of reusing the old element and never registering. Server-side, `pollMatchmaking` calls `notifyMatchFound` after a pairing commits, sending **only to the opponent** — whoever's poll made the pairing is demonstrably in the foreground and already knows. Dead tokens reported by FCM (`registration-token-not-registered`/`invalid-registration-token`) are pruned as they're discovered, so they don't accumulate forever. The whole path is best-effort by design: a denied permission, a missing Play Services, or a failed send never blocks a pairing or a match.
  - **Why this matters more than it looks**: pairing is discovered by client polling, and those timers stall once the app is backgrounded. Without the push, someone who queues and switches away has no way of ever learning they were paired. Their queue entry stays flagged `matched` server-side until collected, so returning to the app at any point still lands them in the right match.
  - **Verified live end-to-end**: a real device registered its token (confirmed present in Firestore), queued through the app, was **backgrounded**, and a second account's poll paired with it — the device received "Opponent found / MMTestA is ready to battle. Tap to start." in the notification shade, confirmed both in `dumpsys notification` and visually.

This works precisely because matched entries are exempt from stale-entry pruning. It also serves as the **in-app indicator** half of this decision, though only in the recovery position — a live indicator while actively queueing still isn't built.

- **Tie votes — DECIDED**: a tied vote results in no rating change for either player (counted as neither a win nor a loss) — simplest and hardest to game, avoids needing a coin-flip or sudden-death tiebreaker mechanic.
- **Blocking — DECIDED**: users can permanently block a specific opponent after a match, preventing future pairing with that person. Combined with the CAPTCHA gate, this is treated as sufficient layered anti-fraud defense; extra friction at voting time would hurt participation without a clear fraud-prevention benefit. Revisit only if vote manipulation is actually observed.

## Ranking System
- **Rating — DECIDED**: Chess-style Elo-like numerical rating system, used as the underlying math (not shown directly to users — see Laugh Meter below). Everyone starts at a flat **1200**. No hard ceiling (unbounded). Soft floor at ~100 (prevents demoralizing bottomless losing spirals).
- **K-factor — DECIDED (variable, not flat)**: use a VARIABLE K-factor rather than one flat rate for all players — modeled on how real chess federations (USCF/FIDE) handle this. Lower/newer-tier players (roughly ranks 1-4) get a HIGH K-factor — bigger rating swings per match, faster early climbing, quick gratification, forgiving of an early loss or two. Higher-tier players (roughly Headliner and up, especially near the GOAT top-5 cutoff) get a LOW K-factor — smaller swings, rating only moves with sustained real performance, every win at the top genuinely has to be earned. Chosen over a hard "different system above X rank" split specifically because a single continuously-scaling K-factor achieves the same early-gratification-then-real-competition FEEL without a jarring rule-change moment a player could hit and feel blindsided by. Exact K-factor values per tier band not yet set — needs real tuning once analytics data exists (see Firebase Analytics decision).
- **Points/currency — DECIDED, separate system from rating**: a second currency that only ever increases (earned via participation, more for wins) — deliberately structured to never go down, unlike rating, so players on a losing streak still have something accumulating (retention/engagement reasoning). Spent on cosmetic-only unlocks (profile borders/frames, badge flair, alternate UI themes) — nothing that affects gameplay/matchmaking.
  - **Real-money purchase — DECIDED: earn-only for V1, revisit for V2**: recommendation was to eventually allow buying points via Apple/Google IAP (low legal risk since it's cosmetic-only, no prize/chance element unlike tournament entry fees) but NOT build this for V1 — validate that the cosmetic-unlock system actually drives engagement with earn-only points first, before investing in payment infrastructure for something unproven.
- **GOAT-tier exclusive perks — NEW, DECIDED (concept only)**: the top rank should unlock something beyond just the badge/title (special cosmetics, priority matchmaking, and/or access to exclusive GOAT-only tournaments) — ties back to original vision of "prestigious status, cool unlocks." ## Content Policy & Moderation
- **Free speech stance (explicit developer decision)**: offensive language, slurs, and no-holds-barred content are ALLOWED by design — this is a comedy platform, not a censored one. Users consent to this on signup.

On detection: auto-blur video feed and/or auto-end the match. This is VISUAL/ACTION moderation only — it does not touch audio, speech, or language, and does not conflict with the free-speech content policy above. ### Recording Consent — IMPORTANT, needs a dedicated UI step

### Random-Stranger-Video-Pairing Design Risk — read before loosening age verification
- Omegle (the best-known random-stranger video chat platform) shut down in 2023 after years of lawsuits alleging the CORE DESIGN — randomly pairing strangers including minors with adults, with minimal age verification — was itself legally defective, independent of what was said/done on any call.
- A court rejected Omegle's Section 230 defense in one case specifically because the claim targeted the product's design (matching mechanism), not the content exchanged. This directly parallels the 2026 CA/MA "negligent design" rulings noted elsewhere in this doc.
- Implication: this app's core mechanic (random stranger video pairing) is the same fundamental risk pattern, even though content differs (comedy vs. the abuse Omegle enabled). The Google Play Age Signals decision is doing real legal/safety work, not just a compliance checkbox — treat any future decision to weaken or bypass it as a serious risk, not a minor product tweak.

## Video Retention Policy — DECIDED, and now ENFORCED
- **BUILT**: `purgeExpiredRecordings` (`functions/recordingRetention.js`, scheduled daily) deletes raw footage for matches older than 7 days, keeping anything marked `recording.published`. Deletion sweeps the whole `match_recordings/{matchId}/` storage prefix rather than the file list stored on the document — a recording that failed to stop cleanly can leave files behind that were never recorded anywhere, and those are exactly the ones that would otherwise linger past the retention promise. The purge decision is a pure function (`purgeDecision`) with 9 local tests, because it irreversibly deletes video of real people and the line between "purge" and "keep" is a promise made in the published Privacy Policy: a bug one way leaks footage past its window, a bug the other way destroys an unrecoverable published highlight. Only an explicit `published === true` counts as published; anything ambiguous falls to purge.
- Only "posted" highlight clips (the auto-edited, publicly shared versions — see Auto-Editing for Highlights) are retained. Raw/unposted match recordings are deleted after **7 days** — long enough to cover the 24-hour vote window plus reasonable report/moderation review time, short enough to control storage cost. This also bounds how long the recording-consent applies (see Recording Consent legal item).

- **Bracket size — DECIDED**: flexible, any number of entrants (not restricted to fixed power-of-2 sizes like 8/16/32/64). TECHNICAL NOTE: this means bracket logic must handle BYES (some players automatically advancing a round without playing) when the entrant count doesn't divide evenly — a real implementation detail to account for, not just a UI/rules matter.
- **Tournament withdrawal — DECIDED**: a user CAN withdraw from a tournament and get refunded, as long as it's before the bracket actually starts. Separate from the "tournament cancelled due to insufficient entrants" refund rule already decided — this is a voluntary individual withdrawal, not a tournament-wide cancellation.
- **Build Order step 8 implementation status**: per a scope-check decision, this covers the core points-based loop only — real entry fees/cash stay schema-only (`entryFee`, `prizeType`, `eligibleStates` exist on the doc but nothing collects or enforces them), since there's no payment processor yet and CLAUDE.md's own Payment Processor / Business Entity Formation sections already defer that trigger to when real money is actually about to go live. Real tournament *creation* is meant to go through the Firebase console (same pattern as profile approval/report review), not a custom admin UI. What's built and verified live end-to-end: `TournamentListScreen`/`TournamentDetailScreen` (join/withdraw, live entrant count via Firestore listeners, bracket display), `functions/tournament.js`'s `generateBracket` (random seeding + bye handling, "golden parachute" cancellation below `minEntrants`) and `debugAdvanceRound` (round-by-round advancement to a single winner), plus a `debugCreateTournament` function that exists PURELY because no admin-console access was available for testing in this environment — real admin use should just create Firestore docs directly in the console per the established pattern, this function should be removed or admin-gated before launch (same caveat as the other `debug*` functions).
  - **Real bug found and fixed**: the first bracket-generation approach shuffled real entrants and null "bye" placeholders together into one flat list before pairing sequentially. That can randomly land two bye placeholders in the same matchup (both players null) — a matchup with no one to advance, silently breaking that entire tournament. Caught by a 2,400-trial local simulation (200 trials each across 12 entrant counts, asserting a valid single winner every time) before ever touching a device — the naive version failed 4 of 12 sizes (5, 9, 17, 1 entrants). Fixed by peeling the correct number of byes off the shuffled entrant list FIRST (which is always possible byeCount is always less than half the bracket size by construction), giving each one its own matchup, then pairing the remainder — guarantees at most one bye per matchup regardless of entrant count. Confirmed live on an emulator with a real 3-entrant tournament (1 bye) advancing correctly to a real winner, not just in the local simulation.
  - Async per-round windows (`windowStart`/`windowEnd`), no-show/forfeit auto-loss, and wiring real tournament matches to the actual match+vote pipeline (rather than `debugAdvanceRound`'s coin flip) are NOT built — `debugAdvanceRound` exists solely to prove the bracket-advancement mechanics (round generation, completion detection) work, not as a stand-in for real match results. Real integration would mean tournament-mode matches write their `winnerId` back into the relevant bracket matchup once `finalizeMatch` runs, which isn't wired up yet.

## Matchmaking Queue Architecture — DECIDED
- Firestore (the primary planned database) is not well-suited to real-time "who's currently waiting to be matched" queue logic — it's built for document storage, not low-latency ephemeral state.
- **DECIDED**: use **Firebase Realtime Database** (a separate, complementary Firebase product optimized for live/ephemeral state) specifically for the matchmaking queue, while everything else (user profiles, matches, tournaments, etc.) stays in Firestore as originally planned.
- **IMPLEMENTATION STATUS — BUILT, deployed, and verified end-to-end against the real backend.** This closes the largest remaining functional gap in the app: before this, there was no way to be paired with a stranger at all, since every match joined a single hardcoded `'test-channel'`.
  - **The RTDB instance had to be created out-of-band.** `firebase database:instances:create` refuses until a default instance exists, and `firebase init database` is interactive, so it was created via the Firebase Database Management REST API (`POST firebasedatabase.googleapis.com/v1beta/projects/{p}/locations/us-central1/instances`) using the website's existing Admin service-account key. That first required a **one-time manual enable of the Realtime Database Management API** in the GCP console — the developer had to click it, since the service account lacks `serviceusage.services.enable`. Same class of one-time console step as Firestore, Storage, and Cloud Vision before it. Instance URL: `https://the-bully-league-default-rtdb.firebaseio.com`, region `us-central1`.
  - **Queue shape**: `matchmakingQueue/{mode}/{uid}` — one queue per mode, so an exhibition player is never paired into a rated match. `database.rules.json` **denies all client access to the entire tree**; only the Cloud Functions (Admin SDK, which bypasses rules) ever touch it. That's deliberate and load-bearing: a queue entry carries the player's real rating, tier, and block list, so a client-written entry would let a modified client claim any rating it liked and hand-pick opponents.
  - **Three callables drive it** (`functions/matchmaking.js`, exported from `index.js`): `enterMatchmakingQueue` (builds the entry from the caller's real Firestore user doc, refuses non-`active` accounts), `pollMatchmaking` (the pairing attempt), `leaveMatchmakingQueue` (idempotent).
  - **The client POLLS rather than subscribing to RTDB** — an explicit design choice, not an oversight. The tier-widening rule is time-based, so something has to re-attempt pairing on a timer regardless; polling makes that the same mechanism instead of a second one. It also keeps `firebase_database` off the Flutter side entirely, avoiding another Android dependency in a toolchain this doc documents as fragile (the AGP pin, the `permission_handler`/`image_picker` conflicts). Cost is one invocation per waiting client every 3s — fine at private-beta volume; the upgrade path if that ever matters is an RTDB listener for the *notification* only, keeping these callables for the pairing itself.
  - **Pairing runs as a single RTDB transaction over the whole per-mode queue node.** Transacting on the parent (rather than per-entry) is what makes the two-sided claim atomic — two separate single-entry transactions could interleave into A-claims-B while C-claims-A. The documented scaling limit is that every attempt reads and rewrites that node; sharding by tier band is the natural fix later.
  - **Rules implemented, matching the decisions already in this doc**: same-tier first, widening by ±1 tier per 30s of waiting so nobody waits forever; two-way blocking (a block is honoured from *either* side, or it would be useless); repeat-opponent cooldown as a **preference, not a filter** (falls back to a repeat rather than stranding the only two people in the queue, per the existing decision that availability takes priority); closest-rating selection with longest-waiting as the tie-break; and pruning of entries abandoned by a crashed client so they can't be paired against.
  - **`recentOpponentIds` is now actually written** (by `completeMatch`, as a `{opponentUid: timestampMs}` map), which is what makes the cooldown real rather than schema-only. The code tolerates the legacy plain-array shape too.
  - **Match documents moved server-side, and this is a real security tightening.** They're now created by `pollMatchmaking` at *pairing* time with `status: 'pending'`, and flipped to `completed` by a new `completeMatch` callable. `firestore.rules` for `matches/{matchId}` went from "either participant may create" to **`allow write: if false`**. The old arrangement let a modified client invent a match between arbitrary players and declare it finished — which is the entry point to the voting pipeline and, for ranked, to real Elo changes, i.e. exactly the class of sensitive write the Security & Compliance Baseline says belongs behind a Cloud Function.
  - **Because match docs now exist before a match is played, everything downstream had to learn about the lifecycle**: `castVote` refuses anything not `completed`; `finalizeMatch` settles a still-`pending` match found by the hourly sweep as `abandoned` with no winner and no rating change (safe, because the sweep only looks at documents already older than the full 24h vote window, so nothing in progress can be caught); and the website's Recent/Trending feeds filter to `status == 'completed'` so in-progress and abandoned matches never surface publicly. The two feed queries needed new composite indexes (`firestore.indexes.json`, previously empty).
  - **`generateAgoraToken` now validates the channel**, closing a gap its own doc comment had flagged as acceptable only while every match shared a test room. Exactly two shapes mint: `precheck_{callerUid}` (the caller's own solo pre-match camera/mic check) and `match_{matchId}` where the caller is one of that match's two players and it hasn't ended. Without this, any signed-in user could mint a token for any channel name and **drop in on a stranger's live match uninvited** — a real eavesdropping hole the moment channels stopped being a shared test room.
  - **The pre-match check now joins its own solo `precheck_{uid}` channel** rather than the real match channel, and runs BEFORE queueing rather than after. Both orderings satisfy "both users must pass this before the match starts"; doing it first means someone sorting out their lighting or a denied permission isn't burning an already-paired opponent's time.
  - **A race fix from step 9a became structurally unnecessary.** Live in-match frame sampling previously couldn't start until an `'identity'` data-channel message delivered the opponent's Firebase uid, because the auto-filed content-violation report needs someone to file against. The pairing now supplies that uid before `MatchScreen` is even built, so sampling starts at join and the race is impossible by construction rather than merely ordered around. The `'identity'` and `'matchSaved'` messages are gone. Violation-ended matches now also settle explicitly as `abandoned` (and the auto-filed report finally carries a real `matchId`, which used to be `null` because nothing was written until verdict time — which a violation never reached).
  - **Testing — two layers, both real.** (1) `functions/test/matchmaking.test.js` runs the pairing rules as pure functions with no emulator or credentials (21 checks, including **2,000 randomised concurrent-queue trials** asserting no player is ever double-booked and every match has exactly two mutually-agreeing participants). This deliberately repeats the approach that caught the tournament bye bug before it reached a device. Run with `node test/matchmaking.test.js` from `functions/`. (2) A scripted end-to-end run against the **deployed** backend with two genuine signed-in accounts confirmed the whole loop: one player queues and correctly stays searching; the second queues and pairs; the first's next poll finds the *same* match rather than creating a second; the document exists as `pending` with both players; token minting succeeds for one's own channels and is **refused** for another user's pre-check channel, for the old `test-channel`, and for a finished match; voting is refused mid-match; `completeMatch` settles it and a duplicate call is a no-op; and the cooldown record is written.
  - **Real bug found by live testing and fixed**: `enterQueue` originally rejected anyone whose user document didn't say `accountStatus === "active"`, which **locked every pre-Build-Order-step-9 account out of matchmaking entirely** — accounts created before that step introduced the field have no value at all. - **Backend**: Firebase — Auth (phone/email/password), Firestore (database), **Realtime Database (specifically for the live matchmaking queue — see Matchmaking Queue Architecture above)**, Cloud Functions (server-side logic — also used to guard sensitive writes like rating/points, see Security & Compliance Baseline), Cloud Storage (recorded videos, avatars), Cloud Messaging (push notifications), **Firebase Analytics (DECIDED — free, built into existing stack, tracks usage data needed to actually tune the many "adjust later based on real data" decisions throughout this plan: round length, points balance, tier thresholds, etc.)**. - **State management — DECIDED: Provider.** Chosen over Riverpod specifically to avoid stacking a fourth new paradigm on top of Flutter/Firebase/Agora, all being learned simultaneously — Provider has a gentler learning curve and is officially sufficient for an app of this complexity per Flutter's own docs. - **Crash reporting — DECIDED**: Firebase Crashlytics (free, integrates with existing stack) — automatic crash detection/reporting.

## Premium Subscription — NEW, DECIDED
Monetization approach: recurring subscription for FEATURES layered on top of the free core loop, NOT gating the core ranked/exhibition gameplay itself (ranked mode, titles, and rating stay fully free — preserves the viral prestige-chasing hook the whole ranking system was designed around). Guiding principle reaffirmed by developer: keep the app authentic, focused on giving comedians an easy platform to showcase talent — explicitly rejected pay-for-visibility (boosting a match's discovery-feed placement) as undermining that authenticity.
- **Clip download — DECIDED**: free tier gets a WATERMARKED highlight clip. Premium subscribers get the FULL, unwatermarked clip/highlight reel download — lets performers share their own wins on their own social accounts. Notable: this is one of the few paid features that also feeds the app's own growth (every share is free organic exposure), funded by the person paying for it.
- **Stats/analytics dashboard — DECIDED**: premium subscription feature. Deeper competitive data (rating history over time, win rate by opponent tier, head-to-head records, round-level breakdowns) — appeals directly to the same competitive-minded users already engaged by the ranking system.
- **Tournament entries — DECIDED**: premium subscribers get a set number of free tournament entries per month (exact number TBD); non-subscribers pay the standard per-tournament entry fee. Ties the subscription and entry-fee revenue streams together rather than having them compete for the same dollar.
- **Explicitly rejected**: paywalling ranked mode itself (undercuts viral growth hook + cold-start problem — new users need to experience the free prestige loop to want to stick around) and paying for discovery-feed visibility boosts (undermines "the funniest content rises" authenticity).
- **Legal note**: a feature-access subscription (not tied to skill/chance/prize) is NOT a sweepstakes/contest-law question like tournament entry fees are — it's a standard SaaS-style subscription, cleanly handled via Apple/Google's built-in subscription APIs.

## Match Recording — BUILT (the prerequisite the whole content pipeline was blocked on)
Until this, nothing anywhere captured any footage — the discovery feed showed metadata only, and every highlight/TikTok plan below was blocked on there being video at all.
- **Agora Cloud Recording, composite (server-side), writing into the project's existing Cloud Storage bucket** (`functions/cloudRecording.js`). Chosen over recording on the devices for three reasons: it survives a client crash, a backgrounded app, or a player force-quitting — which are exactly the matches most worth reviewing; it costs players no upload bandwidth or battery on mobile data; and composite mode produces ONE side-by-side file, which is what a highlight clip actually needs (recording each device separately would mean compositing two files later anyway).
- **Scope honours the existing decision**: ranked and tournament only. Exhibition matches return `mode-not-recorded` — not an error, since not recording them is correct behaviour, and it keeps recording cost off the mode people play most casually.
- **Started by the host device at host-election time**, which is the first moment both players are provably in the channel. Starting at pairing would record an empty room while the second player finished their bio reveal, and Agora bills by duration. Only the host asks, so the two devices don't race; a duplicate is a no-op.
- **Recording can never block a match.** Every failure path — vendor unreachable, credentials missing, start or stop failing — is caught, recorded on the match document (`unconfigured` / `start_failed` / `stop_failed`), and the match proceeds. Stopping happens *after* the match status write for the same reason, so a slow Agora call can't strand a match as `pending`. Agora's own `maxIdleTime` also stops a recording once both players leave, so a failed stop costs the file list, not the footage.
- **The composite is 1080×1920 (9:16 vertical) — CORRECTED from an earlier mistake worth recording.** It was originally 960×360, an 8:3 ultra-wide strip chosen to sit inside Agora's cheap HD billing band. That was wrong for this product: dropped into a 9:16 frame that occupies about a fifth of the screen height with the rest empty, and there is no vertical picture information to recover by cropping — it would have produced unusable clips for the exact channel (TikTok/Reels/Shorts) the entire content strategy depends on. Researched properly: TikTok's documented standard is **1080×1920 at 9:16**, minimum 720×1280.
  - **The cost step turns out to be unavoidable, which makes the decision easy.** Agora bills on aggregate resolution, and *any* genuinely vertical format at or above TikTok's minimum already lands in the Full HD band (921,600–2,073,600 px). The only vertical shape that stays in the HD band is roughly 540×960, which is *below* TikTok's stated minimum. And once you're in the Full HD band, 720×1280 and 1080×1920 cost exactly the same — so full 1080×1920 is simply the best value available. Recording goes from ~$0.015 to ~$0.034 per match (~$19 more per 1,000 recorded matches), which is negligible against the Production quality bar this doc sets elsewhere.
  - **Frame rate and bitrate were raised for free**: Agora bills on resolution and duration only, not fps or bitrate, so 15fps/800kbps (tuned for the tiny old canvas, and blocky at 1080×1920) became **30fps/2500kbps** at zero billing cost.
  - **Verified on a real match**: the produced mp4's own track header reads exactly **1080×1920, ratio 0.5625** — parsed out of the MP4 box structure directly, since no ffmpeg is available in this environment.
  - **Layout is an explicit stack (`mixedVideoLayout: 3` + `layoutConfig`), after "best fit" was tried and proved wrong.** Best fit (`1`) tiles participants **side by side regardless of canvas shape**, so on a 9:16 canvas each player got a narrow half-width column with dead space above and below — caught only by actually watching the output file, since the header reports the correct 1080×1920 either way. Player 1 now occupies `y_axis` 0.0–0.5 and player 2 0.5–1.0, each full width.
  - **This forced a related change: players now join with FIXED Agora uids (1 and 2) instead of the wildcard 0.** A customized layout has to name each region's occupant by uid, and the server has no way to learn a dynamically-assigned one. The uid is decided server-side at pairing (player1→1, player2→2) and carried on the pairing. The token is unaffected — it's minted against uid 0, which Agora treats as a wildcard valid for any uid. Side effect: host election (`myUid < oppUid`) is now deterministic, so **player1 always hosts** rather than it depending on whichever uid Agora happened to assign.
  - **`render_mode: 0` (crop) on both regions**, not fit. Each tile is 1080×960 — wider than tall — while phones publish portrait, so "fit" would pillarbox each player into a narrow strip with black either side. Crop fills the tile and keeps the middle of the frame, which is where the pre-match oval guide already trains players to put their face.
  - **Worth considering later**: since only one player speaks per turn in this format, switching the layout per turn (Agora supports updating layout mid-recording) to full-screen the active speaker would give each roaster the whole 1080×1920 with no cropping at all — much stronger short-form content than a static split.
- **The human review gate exists in the schema from day one**: recordings start `reviewStatus: 'pending'`, `published: false`, and nothing in this pipeline publishes anything on its own — matching the requirement below that a human approve a clip AND separately confirm it won't trip TikTok/Instagram/YouTube's rules, which are stricter than this app's internal speech policy.
- **`storage.rules` denies clients BOTH read and write on `match_recordings/**`.** Write, because nothing in the app uploads footage so any write would be forged. Read, because this is raw unreviewed video of two people — a readable path would route straight around the review gate, letting anyone who could guess a match id pull unreviewed footage of strangers. Agora writes with its own HMAC credentials, which bypass rules exactly as the Admin SDK does.
- **Credentials needed to actually switch it on** (server-side secrets, never shipped to the client): `AGORA_CUSTOMER_ID` and `AGORA_CUSTOMER_SECRET` (Agora's RESTful API pair, **separate** from the App ID/App Certificate already in use — generate in Agora Console → RESTful API), plus `RECORDING_STORAGE_ACCESS_KEY`/`RECORDING_STORAGE_SECRET_KEY` (a Cloud Storage HMAC key pair, from GCP Console → Cloud Storage → Settings → Interoperability, so Agora can write into the bucket). All four are currently set to the placeholder `unset`.
- **Runaway-recording watchdog — BUILT** (`stopRunawayRecordings`, scheduled every 10 minutes). This closes the project's only genuinely unbounded cost path. Agora's `maxIdleTime` stops a recording shortly after the channel empties, but does nothing while clients are still connected — so a wedged state machine or a client that never leaves would bill recording minutes indefinitely with nothing to notice. **A billing alert would only report that after the money was spent; this prevents the spend.** The cap is *derived per match* from the settings stamped on that match rather than being a fixed number, because timings are live-configurable: a flat cap generous enough for a 10-round/120-second format would be far too slack for the 3-round default, and one tight enough for the default would cut off a legitimate tournament format and destroy real footage. 7 local tests pin this across the entire configurable range.
  - **A real design flaw was caught by writing those tests**: the first version used 5 minutes of slack, which meant a *wedged* recording (~8 min) cost more than double a *real* match (~3 min) — the backstop was worse than the thing it guarded. Slack is now 2 minutes. The tests assert on **cost** rather than seconds, since that's the property actually being protected, and note that the 10-minute poll interval dominates anyway, so tuning slack below a couple of minutes buys nothing. Worst case at the most extreme legal configuration stays under $1; the everyday case is a few cents.
- **CONFIRMED WORKING END-TO-END on two real devices.** Credentials are set and a real ranked match produced a real recording: a **3.3 MB composited `.mp4`** of both players side by side, plus 8 HLS `.ts` segments and an `.m3u8` playlist, all under `match_recordings/{matchId}/`. The match document's `recording.files` lists all ten with sizes and content types, and flags the composite mp4 via `isComposite`. Also verified earlier with credentials still unset (the safety property): exhibition correctly skipped, ranked recorded `unconfigured` and started nothing, both completed normally.
  - **Two real bugs were found by that live test, both now fixed** — neither was reachable by the scripted tests, because both needed two genuine clients:
    1. **`completeMatch` had a read-then-write race.** Both devices call it on reaching the verdict; both could pass the `status === 'pending'` check before either wrote, so **both** went on to stop the recording. One stop succeeded and the other came back with Agora's "not recording" error — and the loser's error overwrote the winner's file list, leaving the document claiming zero files for a recording that had produced ten objects. The settle is now claimed in a **transaction**, so exactly one caller proceeds.
    2. **The file list trusted Agora's stop response.** That response only exists when *our* stop request is the one that ended the recording — but Agora's own `maxIdleTime` ends it once the channel empties, and the watchdog can end it too. The list is now read from **Cloud Storage**, which is authoritative in all three cases because the bucket is ours and the files are already there. An "already stopped" error is no longer treated as failure at all: if the files exist, the recording succeeded.
  - **A test recording is deliberately left in place** at `match_recordings/09KQgj1NJx0Vf5iWxhSb/` so the composite framing/quality can be eyeballed in the Firebase console before the editing pipeline is built on top of it.
